Контекст и ТЗ

Задание

Разработать стартовую документацию Я.Трекера под ролевую модель «Бизнес-аналитик».

Контекст

Пользователем данной документации является опытный бизнес-аналитик, который впервые сталкивается с Я.Трекером. Для быстрого старта в работе ему требуется минимально необходимый набор знаний, необходимый для решения рабочих задач.

Требования заказчика

  • Часть 1. Структура раздела. Сформировать иерархическую структуру статей. Исключить избыточность, зафиксировать цели и подтемы для каждой статьи.
  • Часть 2. Ключевая инструкция. Написать полностью готовую к передаче пользователям статью «Создание задачи и основные приёмы работы с ней».
  • Ограничения. Деловой стиль без фамильярности, полная оригинальность без пересказа справки Яндекса, обязательные скриншоты с автономными текстовыми описаниями.

Практический кейс: Фиксация и проведение требования через Яндекс Трекер

6 мин · Статья 2 из 4 · Нужен доступ в Я.Трекер и имя очереди

Результат: научиться правильно оформлять требования, настраивать параметры задачи, управлять декомпозицией и вести коммуникацию с командой разработки.

1. Вводный контекст кейса

Бизнес-ситуация

Команда развития цифровых продуктов работает над сервисом «Личный кабинет» (ключ очереди: LK). По результатам продуктовой аналитики выяснилось, что пользователи часто бросают оформление заказов на этапе оплаты из-за необходимости вводить данные банковской карты вручную[cite: 1].

Для решения этой проблемы бизнес поставил задачу: интегрировать оплату через Систему быстрых платежей (СБП)[cite: 1].

Роль бизнес-аналитика в кейсе

В реальной практике инфраструктура Яндекс Трекера (очереди, права доступа, статусные модели) уже настроена администраторами. Задачей бизнес-аналитика является не администрирование системы с нуля, а работа в существующем контексте команды[cite: 1]:

  • Перейти в рабочее пространство проекта (LK)[cite: 1].
  • Создать задачу с четким, структурированным описанием требования, критериями приёмки и дедлайнами[cite: 1].
  • Прикрепить сопроводительные материалы и чек-лист готовности[cite: 1].
  • Назначить ответственных исполнителей, запустить задачу в работу и вести коммуникацию в комментариях[cite: 1].

2. Пошаговая инструкция по постановке требования

Шаг 1. Выбор очереди и инициация создания задачи

Чтобы задача попала в контекст нужной команды и получила правильный префикс (например, LK-101), её необходимо создавать внутри соответствующей очереди[cite: 1].

  1. На левой навигационной панели Яндекс Трекера нажмите синюю кнопку «+ Создать задачу»[cite: 1].
  2. В левом верхнем углу выпадающего окна выберите очередь вашего проекта — LK: Личный кабинет[cite: 1].

Почему мы делаем именно так: Создание задачи внутри конкретной очереди автоматически привязывает её к доске проекта, настраивает нужный набор полей и обеспечивает правильную маршрутизацию уведомлений участникам команды[cite: 1].

Шаг 2. Заполнение названия и базовой структуры требования

Название задачи должно четко отражать суть доработки, а описание — давать команде разработки исчерпывающий контекст без необходимости уточняющих встреч[cite: 1].

  1. В поле «Название» введите:
    [REQUIREMENT] Добавление способа оплаты через СБП в личный кабинет[cite: 1]
  2. В центральном поле ввода описания разместите структурированный текст требования[cite: 1]:
Задумка
Пользователям неудобно каждый раз вводить данные карты вручную. Оплата через СБП ускорит процесс покупки и повысит конверсию платящих пользователей.

Что сделать (Критерии приёмки):
1. В блок способов оплаты добавить новую кнопку «СБП».
2. На десктопной версии: при выборе СБП генерируется и отображается динамический QR-код для сканирования банковским приложением.
3. На мобильной версии: клик по кнопке перенаправляет пользователя в приложение банка-эмитента (Deeplink).
4. После успешного проведения транзакции статус заказа в ЛК мгновенно меняется на «Оплачено».

Совет по оформлению: Используйте визуальный редактор Трекера (панель инструментов над текстом) для форматирования списков, выделения заголовков и вставки ссылок[cite: 1].

Шаг 3. Декомпозиция работы через Чек-лист

Чек-лист позволяет аналитику разбить верхнеуровневую задачу на подшаги, контролировать промежуточный прогресс и назначать ответственных на конкретные микрозадачи[cite: 1].

  1. Под блоком текстового описания нажмите кнопку + Чеклист[cite: 1].
  2. Последовательно добавьте следующие пункты, нажимая «Сохранить» или клавишу Enter после каждого[cite: 1]:
    • 1. Согласовать с UI/UX дизайн кнопки СБП[cite: 1]
    • 2. Подготовить спеку API для разработчиков[cite: 1]
    • 3. Проверить сценарий оплаты на тестовом стенде[cite: 1]
  3. При необходимости укажите отдельного исполнителя и дедлайн для каждого пункта чек-листа непосредственно в его строке[cite: 1].

Возможности управления чек-листом:

  • Для смены порядка пунктов перетаскивайте их за значок слева[cite: 1].
  • Отметка флажка слева от пункта переводит его в статус выполненного[cite: 1].
  • Нажмите на сам пункт, чтобы отредактировать текст, изменить дедлайн или назначить исполнителя[cite: 1].

Шаг 4. Настройка атрибутов задачи (Правая панель)

Параметры задачи на правой панели определяют приоритеты, сроки и ответственных лиц[cite: 1].

  • Тип задачи: По умолчанию указано Задача (или Требование)[cite: 1].
  • Приоритет: Выберите = Средний (или Высокий, если фича критична для ближайшего релиза)[cite: 1].
  • Исполнитель: Введите имя системного аналитика или разработчика. Если вы сами берете задачу в работу — нажмите кнопку Назначить меня (Я)[cite: 1].
  • Дедлайн: Укажите целевую дату завершения анализа и передачи в разработку[cite: 1].
  • Наблюдатели: Добавьте продакт-менеджера, тимлида разработки и QA-инженера, нажав Добавить меня или выбрав коллег из списка. Они будут получать уведомления обо всех изменениях по задаче[cite: 1].
  • Прикрепить файлы: Нажмите значок 📎 под описанием, чтобы приложить прототипы экранов или OpenAPI-спецификацию[cite: 1].

После заполнения всех атрибутов нажмите синюю кнопку «Создать задачу» внизу экрана[cite: 1].

Шаг 5. Ведение коммуникации и сопровождение в комментариях

После создания задачи вся рабочая переписка, вопросы тестирования и согласования должны происходить внутри карточки задачи в блоке «Комментарии»[cite: 1]. Это создает единый информационный контур и сохраняет историю решений[cite: 1].

Как оставить комментарий и призвать коллегу:

  1. Прокрутите страницу задачи вниз до блока «Комментарии»[cite: 1].
  2. В поле ввода введите текст (например: «Коллеги, подготовил спецификацию API СБП. Просьба провести ревью»)[cite: 1].
  3. Нажмите кнопку @ Призвать под полем ввода и выберите из списка разработчика или техлида[cite: 1]. Пользователь получит прямое уведомление и задача отобразится у него в фильтре «Ждут ответа»[cite: 1].
  4. Для вложения артефактов нажмите Прикрепить файл (или перетащите файл прямо в окно ввода)[cite: 1].
  5. Нажмите кнопку «Отправить»[cite: 1].

Дополнительные возможности комментариев:

  • Ответ с цитированием: Наведите на комментарий коллеги и нажмите Ответить, чтобы процитировать фрагмент[cite: 1].
  • Реакции: Наведите на комментарий и нажмите значок эмодзи (👍, 🚀, ✅), чтобы быстро подтвердить получение информации[cite: 1].
  • Связывание задач: Если в тексте комментария написать ключ другой задачи (например, PAY-42), Яндекс Трекер автоматически создаст между ними межочередную связь[cite: 1].

Шаг 6. Перевод задачи по жизненному циклу (Статусная модель)

По мере выполнения работ аналитик обновляет статус задачи на панели управления (вверху правой колонки)[cite: 1]:

  1. Открыт ➔ При создании задачи[cite: 1].
  2. В работе ➔ Аналитик приступил к проектированию или передал требование в спринт разработки[cite: 1].
  3. Решен / Закрыт ➔ Требование полностью реализовано, протестировано на стенде и задеплоено в пром[cite: 1].

3. Итоговый чек-лист бизнес-аналитика при работе с задачей

Воспользуйтесь этой памяткой перед передачей требования в разработку:

  • Очередь выбрана верно: Задача находится в продуктовой очереди (LK), а не в личной или административной[cite: 1].
  • Заголовок информативен: Указан тип и ключевая суть ([REQUIREMENT] Добавление способа оплаты через СБП...)[cite: 1].
  • Описание структурировано: Присутствует Контекст («Задумка») и проверяемые Критерии приёмки (Acceptance Criteria)[cite: 1].
  • Чек-лист заполнен: Выделены конкретные подзадачи для контроля прогресса[cite: 1].
  • Участники назначены: Указан Исполнитель, заполнен список Наблюдателей и выставлен реальный Дедлайн[cite: 1].
  • Призваны ответственные: В комментариях через @ упомянуты разработчики и QA-инженеры[cite: 1].
